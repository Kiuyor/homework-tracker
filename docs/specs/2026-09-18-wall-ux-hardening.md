# 作业墙体验收口：出口可发现、录入不吞内容、科目可扩、投影看得清

日期：2026-09-18　依据：`CONTEXT.md`、`docs/adr/0001`–`0004`

## 1. 问题陈述

作业墙的使用人已敲定为**一名学生科代表，在一间教室的一台触控一体机上，纯触控+软键盘操作**（ADR-0001）。以此为镜，现存四处缺陷不是打磨问题而是功能失效：

- **出口找不到**：展示态唯一的退回入口是右下角 40px、`opacity:0.25`、图标是"编辑"铅笔的圆钮（`index.html:172-174`、`style.css:848-865`）。`title` 在触控屏永不显示，图标语义反向。而科代表全天在两种状态间双向交替，这个动作每天要成功无数次。
- **全屏会假死**：`main.js:279` 的 `requestFullscreen().catch(function(){})` 使 `?show=1` 冷启动默默以窗口态打开；全屏状态与模式状态互不知情，`body.view-show` 隐藏顶栏且 `overflow:hidden`（`style.css:736-739,977`），页面看起来坏了。
- **录入吞内容**：打字中途手掌碰到遮罩即静默清空（`main.js:123-125`），Esc 同理（`main.js:131`）。纯触控下这不是边角，是日常。
- **三处只进不出的死功能**：`completed` 在渲染层从不被读取（`ui.js:108-147` 无一处引用，`style.css` 无对应样式）；`note` 只有批量栏能写、哪里都不显示；单条编辑的日期无法表达"次日交"，周一录的周二死线会显示成一个已经过去的时刻（`ui.js:234-253`）。
- **科目封闭**：科目完全由 `db.js:112` 种子决定的固定六科，全站没有增删入口，政治/历史/地理无处可录。

## 2. 方案概述

四条线并行，全部落在既有文件内，不引入新框架、不引入构建步骤：

1. **把出口做成明面上的东西**，并让全屏与模式**解耦**（不是同步）——按 ADR-0003。
2. **默认落在展示态**，编辑态显式进入且闲置自动回弹，两个方向都不会把错误界面留给全班。
3. **保留居中模态，只修触控人机工程**，并把"改一两条"这条主动线的三处断点接上（内容不被吞、死线能表次日、~~科目可自由输入~~←该半边已由 ADR-0011 收回为六科闭集）。
4. **做减法**：删掉完成态、备注、批量导入、批量编辑，把省下的屏高与注意力还给唯一操作人。投影侧另定降级顺序：先压间距行高，仍不够才轮播分页。

## 4. 已定决策

| 决策 | 取舍理由 | 出处 |
| --- | --- | --- |
| 单设备零鉴权 | 引入权限是数量级成本，且威胁模型是物理接触 | ADR-0001 |
| 展示态为默认常驻态，编辑态显式进入 | 记住上次模式会在刷新瞬间把删除钮暴露给全班 | ADR-0003 |
| 编辑态闲置 5 分钟自动回弹 | 封住"科代表改完走人"的反向风险 | 本次拷问 |
| 出口做成带文字胶囊 | 触控下 `title` 永不显示、0.25 透明度等于不存在 | 本次拷问 |
| 继续用 Fullscreen API，但**与模式解耦** | 需要那条地址栏高度；而 Esc 退全屏无法被网页取消，只能解耦 | ADR-0003 |
| 模态不再响应 Esc | 我们与遮罩点击同属"静默吞内容"的同一类 | 本次拷问 |
| 遮罩点击不关闭模态 | 触屏误触率下，从源头消除比弹框确认更彻底且零打断 | 本次拷问 |
| 保留居中模态，不改成行内/抽屉 | 单一动线，避免新增与编辑两套 UI | 本次拷问 |
| 截止时间加"当天/次日"两选 | 覆盖"周一录周二交"这一真实主流，比任意日期选择器便宜得多 | 本次拷问 |
| ~~科目自由输入自动建科~~（已由 [ADR-0011](../adr/0011-subjects-are-a-closed-set-of-six.md) 收回：六科闭集） | 当时的判断是"真实班级科目数不由软件决定"；库里 0 行表外科目证伪了它 | ADR-0004 → ADR-0011 |
| 删除完成态/note/批量导入/批量编辑 | 写进去没人看得见的字段就是噪声 | ADR-0002 |
| 投影降级：先压间距行高，再轮播分页，不退回滚动 | 后排看不见即功能失败，而教室后排没人能滚动那面墙 | ADR-0004 |
| 展示态要有专属空态文案 | 零作业时展示态复用编辑态那句"今天还没有作业"，且写死"今天"二字（原判断"六个格子挂暂无作业"已被工单 01 实测推翻，见故事 38） | 本次拷问 + 工单 01 实测修正 |
| `completed`/`note` **两列原地保留**，只删 UI 与后端写入路径 | 便携版带着有真实数据的 `homework.db` 分发，项目无 migration 账本；不可逆 `DROP COLUMN` 的收益只是两列沉默字节 | 已回填 ADR-0002 |

故事 44/47 即为这条决策的落地验收。拆单时不需要再回到这个问题。

## 5. 测试决策

**复用的既有接缝（优先）**

1. **HTTP API 接缝**——`test/api.test.js` 已是一层跑在 express app 上的 `node --test`。落在这一层的验收：故事 27/28/29（原为"自动建科的幂等"，ADR-0011 之后是同一条接缝上的**反向**验收：表外名 400 且不落库）、43（batch 路由消失）、44（`completed`/`note` 不再被接受）、19/20 的后端半边（当天/次日落到 `deadline` 的日期部分）。
2. **`window.parseDeadlineInput(text, baseDateStr)`**——已是纯函数形态、已是 `ui.js:234-253` 的唯一解析入口。故事 19/20/21 的前端语义扩在它的签名上（多一个"当天/次日"入参），**不新建第二个解析函数**，因此 `formatDeadline` 侧的渲染断言保持有效。

**为故事 4/6/10/12 这些状态机行为，仓库当前没有浏览器测试基座**（无 Playwright/无 jsdom 装配）。决定：**本次不引入**。这些故事改为一份可手工执行的验收清单（下面第 6 节的"完成定义"），由人在真机或 DevTools 触控模拟下走一遍。这条边界必须写明，否则"测过了"是空话。

**完成定义**：`npm test` 全绿；API 层新增断言覆盖 27/28/43/44；手工清单覆盖 1-14 与 32-37 每一条，且在**触控模拟 + 1366×768 与 1920×1080 两档分辨率**下各走一遍（一体机常见分辨率偏低）。

## 6. 明确不做

- **不做鉴权、不做口令、不做多班多师隔离**（ADR-0001）。
- **不做科目管理页**（改名/改色/排序/停用），也不做拖拽排科目（ADR-0004）。
- **不做行内编辑、不做底部抽屉**——模态形态保留（本次拷问）。
- **不引入浏览器端测试框架**。
- **不做任意日期选择器**——只到"当天/次日"这一粒度。
- **不改"保存后关窗 + 全量 refetch"** 的不乐观更新策略。
- **不改视觉基调**：白板风、系统字体栈、12 色池、暗色模式、`prefers-reduced-motion` 均维持。
- **不碰轮播之外的展示层布局实验**，不碰 `renderSignature` 的跳过重渲染机制。
- **不动 `/api/homeworks/reorder` 与拖动排序**。
- 以下遗留缺陷**本 spec 不覆盖，只登记**：`index.html:5` 的 `user-scalable=no` 使编辑态失去唯一放大手段（A−/A+ 仅存在于展示态）；顶栏 `collapseBtn` 收起后按新的"出口必须带文字"标准仍属图标暗号；`?show=1` 隐藏顶栏导致学生永远看不到别的所属日。

## 7. 补充说明

- 现有测试里 6 处与 `note`/`batch` 直接绑定（`test/api.test.js:90,116,146,154,162,241`），故事 43 落地时它们必须随之删除，**不是改绿而是删掉不再成立的断言**——拆单时把这件事与被删的路由放在同一张票里，避免有人为了跑绿而复活功能。
- `ui.js:4-12` 的 `subjectColor` 用 `idx % SUBJECT_COLOR_COUNT` 取模。故事 31 之所以能只靠"科目名一直在文字里出现"结案，前提是分组标题始终渲染 `subject-name`（`ui.js:87-89` 已核实）。若未来有人把标题改成纯图标/纯色块，这条依据即失效。
- ~~故事 30 的"其他"分组在自动建科后不再由新录入产生，但**历史数据仍可能 `subject_id` 为空**，其渲染兜底不可删。~~ → **本条已被 `docs/specs/2026-09-19-one-homework-per-subject.md` 故事 6 + ADR-0005 后果 3 推翻**：查库结果是 0 条 `subject_id IS NULL`，"历史数据仍需可见"这个前提当时就不成立；分组与兜底已于工单 021 删除，科目改为必选。

- `AGENTS.md` 的高危命令闸门适用于故事 44 与第 4 节的 DB 立场：任何 `DROP COLUMN` 都属于必须先向使用人说明影响并等其明确回话才能执行的类别。
